# 实施流程

## 范围与隔离

正式需求或 Bug 按以下顺序接入工单：

- 用户给出编号或链接：从工程配置的 Gitea 仓库读取描述、评论与验收条件，再定位和实施；不能只凭聊天摘要猜测工单内容。
- 用户未给编号：先创建包含诉求、范围和验收条件的工单，取得编号后实施。若是在继续当前已有明确关联的任务，复用原工单，不重复创建。
- 在工程已有授权内直接创建与回写，不要求用户代建。连接或权限不可用时说明实际阻碍，不虚构编号或同步成功；继续可独立完成的只读定位，恢复连接后补齐工单再实施。

实施前确认修改端：先读取当前任务对话及工单中的已确认范围；已有明确结论时沿用。用户未明确修改端且既有记录也未确认时，必须询问“这次修改 Web、小程序、移动 OA、其他端中的哪些端，还是所有相关端？”，选项按工程实际应用列出；截图或当前打开的目录仅作定位线索，不能代替范围确认。

等待答复时可只读定位、创建或更新工单并标记“修改端待确认”，确认前不修改业务代码，也不默认只改当前端或全部端。收到答复后将具体应用清单及验收范围写回工单；“所有端”落实到实际应用清单。若共享后端/API 的拟议变更会影响确认范围之外的端，先说明连带影响并确认范围扩展，再实施。

按工程集成分支准备任务分支及 worktree；继续同一任务先核对已有隔离目录并复用。优先宿主原生工具，不支持目标仓库时使用工程约定 fallback。原目录的未提交改动保留原地。测试数据库、端口、密钥需独立安排；不默认访问真实业务库。

读取涉及应用的规则和环境条件，实施前按[测试责任](testing.md)确定由 Agent 还是用户执行测试。局部 Bug 定位原因并提供回归覆盖点；用户测试模式不由 Agent 执行复现或回归测试。功能实现以已确认规格为输入。

## 界面

复杂且无工程内参考的界面先创建 Figma 原型并关联具体节点，用户验收通过才继续代码。用户明确“直到代码完成再验收”时，只免除该任务中途人工验收；原型、自检、最终验收仍保留。Figma 不可用时说明缺口，不能以直接编码等同已完成原型。简单界面或有匹配参考时复用现有模式。

## 工程卫生与沉淀

临时文件写入工程配置的本地目录；需要长期保留的有效经验整理入知识目录，并引用复现、原因、修复及验证证据。规范性结论更新对应权威规则，不仅藏在复盘里。

清理前核对代码、测试、脚本、部署和文档引用；名称、日期或一次检索无结果不是删除依据。生产和测试密钥存外部受控位置，仓库只记录样例、名称及来源。现有目录按职责映射，不随意新建平行体系。
