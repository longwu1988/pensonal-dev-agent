# 实施流程

先按[任务级别](task-levels.md)确认当前为 L1 或 L2。L1 走下方[轻量路径](#l1-轻量路径)；L2 走本节完整顺序。执行中发现应上调时按 task-levels 处理。

## L1 轻量路径

适用于范围明确的单点修复或小改：文案、配置、局部逻辑、有明确同类参考的界面微调；且不改业务规则、跨模块 API 或架构。

1. **范围**：修改端已能从对话、打开目录或单端工程唯一推断时，沿用该端，不强制一分钟改端问答。多端工程且无法唯一推断时先确认，或升为 L2。
2. **工单**：用户给出编号时按占用规则领取；读正文与当前相关评论即可，不默认翻完全部历史。无编号的明确小修可不建完整规格与 OpenSpec change；发现规则/API/跨模块变化则升 L2 并补工单/规格。
3. **隔离**：优先复用当前会话已有任务分支或 worktree；无需为每个 L1 新建隔离目录。全新并行正式单仍按[工单占用](issue-claims.md)处理。
4. **界面**：涉及布局/样式时先读[界面规则](ui-design.md)，过 Figma 门禁；不需要原型则留下视觉依据后实现；需要则走原型确认。
5. **验证**：按[测试责任](testing.md)做受影响范围的最小验证；未跑过的测试不视为已通过。
6. **交付**：用户未要求提交、合入或关单时，实现与验证后停在可续接状态，不自动跑完整[交付流程](delivery.md)。用户明确要求时再读收尾与 PR 规则。

## 范围与隔离

接入或执行中遇到关键未知项，按[关键疑问先澄清](planning.md#关键疑问先澄清)暂停依赖该决定的部分；以下工单、修改端与界面门槛仍适用（L2 默认全适用；L1 以轻量路径的收窄为准）。

配置应用认证或使用工单、仓库、服务器、设计平台账号时，先按[凭据用途与来源](credentials.md)区分运行配置和 Agent 操作凭据，再查对应来源、处理缺失项。

正式需求或 Bug 按以下顺序接入工单：

- 用户给出编号或链接：按[工单全文、评论与图片](issue-context.md)读取工程配置仓库的完整上下文，再定位和实施；不能只凭聊天摘要猜测工单内容。
- 用户未给编号：先创建包含诉求、范围和验收条件的工单，取得编号后实施。若是在继续当前已有明确关联的任务，复用原工单，不重复创建。
- 在工程已有授权内直接创建与回写，不要求用户代建。连接或权限不可用时说明实际阻碍，不虚构编号或同步成功；继续可独立完成的只读定位，恢复连接后补齐工单再实施。

取得编号后，所有正式任务先按[工单占用与隔离](issue-claims.md)核对并领取：普通明确指定单用 queue-claim，自动队列用 queue-next。未取得本会话占用前只读定位，不创建第二份任务实现；不因“手动指定编号”绕过已在处理/已完成记录。只有完整安装运行时才提供该隔离保障。

新建工单、续接任务及交付前，同样按[工单上下文](issue-context.md)核对全部评论与图片的补充和变化。

来自[工单队列](issue-queue.md)的任务复用已领取编号与检查点，按本流程完成单工单实施；领取、阻塞、停止和续接遵循队列规则。队列控制不会替代下述范围确认、原型或测试责任。

实施前确认修改端：先读取当前任务对话及工单中的已确认范围；已有明确结论时沿用。用户未明确修改端且既有记录也未确认时，必须询问“这次修改 Web、小程序、移动 OA、其他端中的哪些端，还是所有相关端？”，选项按工程实际应用列出；截图或当前打开的目录仅作定位线索，不能代替范围确认。

等待答复时可只读定位、创建或更新工单并标记“修改端待确认”，取得用户选择或按统一一分钟策略采用推荐前不修改业务代码，也不默认只改当前端或全部端。取得决定后将具体应用清单及验收范围写回工单；“所有端”落实到实际应用清单。若共享后端/API 的拟议变更会影响确认范围之外的端，先说明连带影响并确认范围扩展，再实施。

先按[PR 合并方式](pull-requests.md)确认本任务交付路径并核对已有 PR；按工程集成分支准备任务分支及 worktree，继续同一任务先核对已有隔离目录并复用。创建或复用前读取[路径、命名与归属检查](worktree-layout.md)，按宿主原生或工程 fallback 规则安排实际目录。原目录的未提交改动保留原地。创建/复用后按[worktree 生命周期](worktree-lifecycle.md)在主目录登记归属、分支与恢复线索；旧目录归属不明时保留。本机运行目录、端口、配置、数据隔离及切回集成版本的方式按[本机环境验证与集成](local-validation.md)提前安排；不默认访问真实业务库。

读取涉及应用的规则和环境条件，实施前按[测试责任](testing.md)确定由 Agent 还是用户执行测试。局部 Bug 定位原因并提供回归覆盖点；用户测试模式不由 Agent 执行复现或回归测试。功能实现以已确认规格为输入。

## 界面

界面实现及布局样式修改读取[界面一致性、原型与验收](ui-design.md)，先确定同端同类参考和复用依据，再按 Figma 门禁决定是否原型确认，并完成视觉验收；门禁跳过或用户免除原型时仍执行视觉依据与一致性要求。

## 工程卫生与沉淀

安装、更新依赖或下载构建工具前读取[依赖下载与镜像](dependency-downloads.md)，按当前环境选择来源并核对安装结果。

临时文件写入工程配置的本地目录；需要长期保留的有效经验整理入知识目录，并引用复现、原因、修复及验证证据。规范性结论更新对应权威规则，不仅藏在复盘里。

清理前核对代码、测试、脚本、部署和文档引用；名称、日期或一次检索无结果不是删除依据。凭据按[用途与来源](credentials.md)分开管理，并区分环境，版本管理只记录空值样例和来源。现有目录按职责映射，不随意新建平行体系。
