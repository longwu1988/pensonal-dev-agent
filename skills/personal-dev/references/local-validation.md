# 本机环境验证与集成

本文件定义 worktree 里单元测试通过后，如何串行合入集成分支。测什么以[测试规则](testing.md)为准：worktree 只要求受影响代码的单元测试通过。整体构建、启动和关键路径由用户在合入后的集成分支上自行验收。远端动作遵循[交付授权](delivery.md)。这是 Agent 工作流程，不是自动启停服务或部署脚本。

## 适用范围与准备

应用代码有行为变化时，在对应 worktree 运行受影响的单元测试。纯文档等不影响运行的任务，记录“不适用”及依据，执行对应文档或静态检查，不为此构建或启动应用。相同代码树可复用已通过的单元测试证据；冲突处理或目标更新改变代码树时重跑受影响单元测试。

多个 worktree 可以同时开发、同时跑各自的单元测试。写入同一个集成分支必须按下一节串行，避免同时合入造成冲突或互相覆盖。

默认在合入前不切换共享端口、容器、数据库或构建产物，也不为本单启动服务。用户另行要求操作共享环境时，先保留最小环境清单：集成分支与当前远端提交、任务分支/worktree、实际运行目录、入口与端口、配置来源、数据环境和启停权限。只记录来源和可核对版本，不记录密钥值。使用前按[资源互斥](issue-claims.md#共享环境与合并排队)取得 `environment:约定名称`，忙则等待；同一物理环境所有会话必须用相同名称。worktree 分开不等于运行环境已经分开。

## 跨工程运行环境隔离

只有实际操作共享运行环境时才适用本节。同机多个仓库或同仓库多个 clone 并行时，先记录各环境的实际主机/容器运行上下文、监听地址与端口、Docker Compose 项目名、显式容器名、网络/卷、数据库/schema、缓存键前缀和对象存储路径，以及当前使用者。只记录与任务有关的来源与定位，不存凭据，也不遍历无关工程的私有文件。

- 默认给不同工程/任务独立的运行标识，可用[工程标识与任务短 ID](worktree-layout.md#新建命名)组合，并适配实际工具的长度与字符限制。Compose 显式使用独立项目名；固定 `container_name`、external 网络/卷和主机绑定目录仍须单独核对，不因项目名不同认定全部隔离。已有稳定环境配置优先保留，不擅自改名迁移数据。
- 端口按工程约定分配并检查实际占用，记录最终入口；预检查不等于保留端口。启动时绑定失败则报告或换用获准的空闲端口，不停止其他工程进程抢占。服务启停仍需原有授权。
- 测试写入使用独立数据库/schema、缓存命名空间及存储路径；是否真正隔离以应用配置和实际连接为准。不把生产数据或共享可变测试数据当作临时环境，迁移或重置另核对权限。
- `environment:*` 和 `integration:*` 的远端锁都只在各自 Git 仓库生效。不同仓库拿到同名锁，不能证明互斥；本机停止令牌也不控制其他工程。必须共用同一物理资源时，先落实覆盖全部使用者的既有协调机制，并保留实际占用证据。缺少可靠跨工程机制时暂停该环境操作，可继续独立的代码和单元测试。

当前个人智能体没有跨仓库的全局环境锁或自动端口分配器。以上是执行规则，不是安装后自动完成环境隔离。

## 验证与集成顺序

1. **任务版本验证**：在任务分支/worktree 运行受影响代码的单元测试，记录命令、提交和结果。不执行构建、打包、启动或集成冒烟。失败留在任务分支修复，不进入合入。
2. **准备合并结果**：读取最新远端集成分支，与已通过单元测试的提交比较，在任务分支上用 Git 合并处理冲突。不把 worktree 文件复制覆盖主目录。代码树变化时重跑受影响单元测试；相同代码树沿用原证据。
3. **串行合入**：单元测试证据覆盖即将合入的代码树后，进入 ready_to_merge，按[合并排队](issue-claims.md#共享环境与合并排队)取得 `integration:集成分支` 锁再进入 merging。同一仓库、同一集成分支，同一时刻只允许一个 worktree 写入合并结果；其他任务保持等待。取得锁后再次核对目标未变化，按选定方式和授权合并 PR，或在明确直接合并模式推送集成分支。目标又有新提交时退出本次合并，重新准备候选并补跑单元测试，不能强推。任务分支提前推送只用于备份和审查，不算主版本已交付。
4. **留给用户的整体验收**：合入成功后在工单写明构建、启动、前后端连通和关键路径由用户在该集成分支上后续验收。这项记录表示尚未由 Agent 执行，不能写成通过。同步本地集成分支与远端。本单没有切换本机运行环境时，记录未改动及这条理由；曾经改动过运行环境时，先恢复到本次集成结果再继续收尾。
5. **回写与关单**：上述单元测试、串行合入和记录都完成后，才按交付流程回写并关闭工单。构建验收未做不阻止这一步，但工单评论必须保留“构建与整体验收留给用户”。

## PR 合并前的候选验证

先以最新目标分支和任务提交准备本地合并候选，确认单元测试证据覆盖该候选代码树，再合入远端。记录目标 SHA、候选代码树和单元测试证据。本地主分支可以暂留原提交，避免生成与平台合并策略不同的本地历史。

合并前核对 PR 的 base/head、拟合并内容及仓库已有的必需检查。平台使用 squash/rebase 时提交号可变化，最终内容必须对应已跑过单元测试的候选。无法证明结果一致或目标已更新时重新准备并补跑受影响单元测试。合并后拉取平台结果，安全同步本地集成分支。不通过自动关单关键字跳过收尾记录。

## 失败、用户自测与停止

- **单元测试失败或冲突未解决**：记录失败阶段、提交和原因，暂停远端集成分支更新与关单。保留未推送合并和用户改动，在原任务分支/worktree 修复后重新跑必要的单元测试并重新排队合入。不直接在集成分支上打补丁。恢复时先核查未提交内容，不用破坏性重置掩盖失败。
- **远端已合并但本地同步失败**：如实记录远端已变化，保持工单未完成，继续按已有授权处理；不强制改写远端历史。
- **用户自测**：单元测试和约定检查由用户执行，Agent 只做源码和 Git 核对，并交付分支、提交和步骤。用户确认该提交通过后才进入串行合入。构建与整体运行验收仍在合入之后由用户完成。用户要求必须等回复时保持等待。
- **用户停止队列**：停止优先，保存阶段说明，不继续测试、合并或推送。续接先核对实际分支、锁和远端状态。

交付证据统一保留在既有工单或任务记录中：任务与集成提交、单元测试命令和结果、串行合入结果、构建验收留给用户的说明，以及未解决项。无需为每次合入新建永久报告。
