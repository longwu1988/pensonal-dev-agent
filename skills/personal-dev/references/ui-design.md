# 界面一致性、原型与验收

适用于界面实现和布局样式修改。新页面、新弹窗及用户要求的视觉改版须经过下述 Figma 确认；纯文案纠错、无视觉变化的后台逻辑和恢复已确认设计的局部修复不新增原型，按影响验证。

## 先确定视觉依据

在现有工单或设计记录中留下简短的“视觉依据”，不为每次任务新增永久报告：

- **同端同类参考**：查目标端规范、组件目录及相近业务，记录可用参考的路径/节点、适用场景。区分确认提示、表单编辑、选择器和详情；按交互类型选择，不能仅因名称含 Dialog 就套用。已有参考可运行时按测试责任查看实际效果；不可查看时说明缺口。
- **复用决定**：记录复用的组件与变体、Token 来源，以及本次差异及原因。优先复用符合规范的完整组件；只有能力缺口明确时才局部扩展或新增，避免复制一组 CSS 后混搭原生控件。没有同类参考时，以目标端规范建立候选设计。
- **冲突处理**：已明确的本任务用户决定与原型、工程现行规范共同作为依据；旧实现和旧 Token 是待核对证据。发现冲突先追溯适用范围，无法判定再询问具体差异，不凭最近找到的页面定标准。任务级视觉例外不自动修改全局规范。

颜色、字号、间距、圆角及控件状态来自所选依据；Figma 也复用这些依据。跨端共享业务语义，各端保留其已确认设计体系。

## 先设计，再实现

1. 按上述步骤确定视觉依据与影响范围。简单、单字段、已有匹配组件或时间紧，都不免除本流程；复用资产应体现在原型中。
2. 使用 Figma MCP 创建可编辑原型，覆盖任务涉及的主要尺寸、输入、加载、错误和提交状态。检查文字、间距、按钮、滚动及安全区；向用户提供具体文件/节点链接和可查看的预览。
3. 在工单或工程指定的设计入口记录原型链接、版本及“待原型确认”。只有用户明确确认该方案后，才开始业务界面代码；生成成功、Agent 自检通过、用户沉默或“先做完再看”都不代表原型获批。已有针对同一版原型的确认直接沿用。
4. 将原型元素映射到已选组件、变体和 Token，按确认的原型实施并完成下述视觉验收。若后续明显改变布局或交互，更新原型并再次确认受影响部分；原型确认不替代最终功能验证。

为制作原型生成的临时 HTML 或设计脚本存放在工程规定的临时目录，不作为已经批准的业务实现提交。

## 唯一默认豁免

用户明确表示本任务“不用生成 Figma 原型”或同等意思时，记录原话含义、任务和范围后直接继续，不重复请求同一豁免；仍遵循视觉规范、必要澄清与最终验证。豁免仅限明确范围，不推广到后续任务。

用户只说“赶时间”“复用现成弹窗”“代码完成再验收”，不能推断为不用 Figma。需要确认的是已有具体原型或明确的豁免，不能先完成业务代码再补图。

Figma 连接或权限不可用时，说明实际阻碍，继续独立工作；依赖原型的界面实现保持待处理。只有用户明确豁免本任务原型后才能跳过，不把其他工具截图称为已完成 Figma 原型。

## 实现后的视觉验收

按[测试责任](testing.md)执行：Agent 模式实际打开待验收版本，在工程要求的尺寸与必要状态下截图，逐项比较“批准原型（若有）—实际界面—同端参考”；用户模式不代跑测试或构建，交付同样的视觉核对点、原型及准确版本，等待用户确认。编译和功能测试通过不能替代视觉验收。

核对内容包括布局与信息层级、字体/间距/圆角/颜色、按钮尺寸与主次、原生控件默认边框/行高/内边距，以及空值、加载、失败、保存中、长内容、键盘和安全区等受影响状态。记录截图位置、运行版本、视口、差异与结论；临时截图遵守工程临时目录约定，使用合成或脱敏数据。必要渲染环境不可用时标为待视觉验证，不凭源码或 Figma 截图宣称实际界面通过。

实现偏离已确认设计时先修复；设计本身需要改变时按原型确认规则处理。明确免除 Figma 只省去原型，不省去视觉依据、组件复用和实际效果验证。

## 将有效设计留给下一次任务

验收通过后在工程现有模式索引中记录“适用交互、组件/页面路径、设计依据、关键状态及限制”；没有索引时在现有 UI 规范入口保留简短引用。业务尺寸和色值留在工程，个人 Skill 只沉淀方法。首次实现可作为局部参考；出现多个真实复用点且接口稳定时再提取共享组件，迁移已有页面单独确认范围，不借单个弹窗任务全仓替换。
