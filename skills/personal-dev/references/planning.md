# 建设与规格

空白工程先从整体需求确认用户、核心业务、应用范围、验收、部署约束与技术栈，再确定目录职责及环境。只创建已确定且需要的目录；不复制试点的四应用结构或历史版本。

既有工程先沿用稳定选型。技术调整记录原因、影响、迁移和验证，重要选择按下述统一提问策略取得决定后实施。

确定依赖安装、工具链与 CI/Docker 构建方式时，读取[依赖下载与镜像](dependency-downloads.md)，将适用的源配置纳入工程现有环境说明。

安排账号与环境时，按[凭据用途与来源](credentials.md)分别确定应用运行配置和 Agent 操作账号的来源；接入说明只记录来源，不集中复制真实值。

正式功能关联工程指定工单。新能力、业务规则、跨模块或 API 变化使用 OpenSpec：在 `openspec/changes/<change>/` 保存 proposal、design、tasks 和 specs；各产物分工，不在工单和另一套 plans 目录复制完整正文。工单保留诉求、验收与链接。

恢复已约定行为的局部 Bug 转实施流程，保留复现/修复/回归证据；发现规范本身需要变化才升级为规格变更。

新工程按[打包与 CI 选型](delivery.md#打包与-ci-选型)确认实际交付方式；Drone + Tag 仅作为可选模式提示，其他 CI、人工打包或无需打包均可。已有明确方案沿用，未选定 CI 不阻塞独立开发。

## 关键疑问先澄清

本规则贯穿接入、文档、原型与开发，不只用于新工程。

1. **尽早识别**：发现会影响范围、业务规则、权限、数据口径、验收或重要技术选择的疑问，先查当前对话、工单及适用规范。已有明确答案直接沿用；仍无法判断时，在定稿相关规格或开展依赖它的开发前向用户确认，不等到整套文档或代码完成才问。
2. **集中提问**：将当前已发现且需用户决定的问题按依赖关系归并，每题给出推荐答案、理由及主要影响；有合理备选时一并列出，避免逐条碎片追问。需要核实的事实提供推荐核实路径，不猜测事实作为答案。不要求一次预见所有后续问题；新增疑问发现后及时提出。遵循现有规范且不改变外部行为、范围或验收的命名、文件内组织等实现细节由 Agent 决定。
3. **等待期间**：可以只读调查、建立工单、记录待确认项、准备明确标为候选的方案或原型；也可继续已经授权且不依赖该决定的工作。未确认的假设不得写成正式结论，不定稿相关规格、不实施依赖它的业务代码。满足下述默认选择条件时，可采用已展示的推荐方案；其他问题继续待确认。统一策略覆盖 Figma、测试责任和方案选择等阶段，但超时选择不记为用户亲自验收、事实证明或操作批准。
4. **决定后落实**：在现有工单或决策入口记录答案、范围及依据，区分“用户明确确认”和“按默认策略超时采用推荐”，更新相关文档后继续，不新增重复报告、不重复询问同一已确认事项。已有文档不构成业务规则已获批准的证据。
5. **中途出现疑问**：暂停受影响部分，说明未知项及影响并澄清；保留独立工作进度。若新结论改变原有范围或已批准原型，按对应确认流程处理，不能用前一次确认覆盖新的决定。

发出确认问题后按[本地语音提醒](question-notification.md)播放固定音频；一次提醒不改变该问题的等待或批准条件。

## 发问前检查

每次发送确认问题（含调用宿主提问工具）前，逐题完成以下检查；缺项先改题，再发送。这里是 Agent 的执行步骤，尚无自动拦截宿主问题卡片的校验器。

1. **区分决定与事实**：明确本题让用户选择的下一步，以及仍待核实的事实。“已放行”“已登录”“已测试通过”只能由用户回复或实际核实支持；改为推荐核实路径或已授权的独立工作，不把事实确认设为超时默认答案。
2. **展示推荐**：有选项时，推荐项放第一项，标签明确带“（推荐）”；宿主指定其他标记格式时遵循宿主格式。题干写出推荐理由、主要影响和未完成项，选项与题干指向同一动作。纯文本/自由输入题也在题干写出推荐下一步；没有可执行动作时推荐保留待办并等待所需信息。默认排序、预选和语音提醒均不能代替可见推荐。
3. **写清等待方式**：对当前授权内可委托选择的下一步，写明“发送后 60 秒未回复，按默认策略采用此推荐”；缺授权、用户明确等待、宿主要求必答或其他前置条件不满足时，写明“本题保持等待，不能通过超时继续受阻操作”。若存在已授权独立工作，明确其范围和仍受阻部分，必要时将“下一步怎么安排”与“操作是否完成”分开；没有独立工作时不承诺到期推进。
4. **确认能执行计时**：确认有可用的异步提问与时间工具；实际发送后记录发送时间、题目版本、推荐动作和截止时间，继续处理新回复并按下一节决定是否执行。若宿主提问会阻塞到用户答复、会话即将结束或无法可靠计时，先说明不能保证 60 秒自动继续，默认采用是 Agent 调整后续动作，不代用户点击、提交答复或假定卡片自动关闭；也不擅自启动后台调度。
5. **修复漏项旧题**：已发送的题若遗漏推荐、推荐标记或超时说明，补齐后重新发送完整问题，注明替代原题、原题不作超时选择；从重发时重新计时，不能按旧发送时间直接采用。重发前先检查新回复：用户已有明确答案时直接沿用，不重复询问。

端口放行示例（已授权服务器内部只读检查，仍有内部检查未完成）：

> 当前公网入口未验证，缺少云控制台操作条件。推荐先完成剩余内部检查，将公网访问保留为待放行后复验，避免阻塞独立工作。发送后 60 秒未回复，按默认策略采用该安排；不会据此认为端口已经放行，也不标记公网验收通过。
>
> 1. 继续内部检查，保留公网待验证项（推荐）
> 2. 我已放行端口，请复验公网入口

收到第二项明确答复后按已有授权复验；原任务已授权独立探测时，也可据真实结果核实公网状态，不写成用户确认。内部检查已全部完成时，不虚构剩余任务：推荐保存部署结果和公网待验证项，等待用户放行；已授权的内部部署与尚未通过的公网验收分别报告。

## 提问推荐与一分钟默认选择

本体系**默认启用一分钟推荐选择**：任务使用本技能时无需先询问是否启用，也无需每次任务重新开启。默认仅处理当前已授权任务内可由 Agent 选择的流程决定，覆盖 Figma、需求、选型、范围及测试责任等阶段；是否能继续取决于实际前置条件。安装或升级不会授予外部操作权限，不代替必需的回答、批准或真实验收，也不会启动后台计时服务。

**关闭与恢复**：用户说“关闭一分钟默认选择”时按明确的工程/任务范围关闭；只对当前问题说“必须等我回复”或“先等等”时停止该题计时，不推定关闭整个工程。工程自己的规则已明确关闭、要求人工确认或更严格等待时继续沿用，升级不覆盖；工程级选择简短记在 AGENTS.md 非受管区或其既有引用规则中，任务级选择记在现有任务记录，不新增 project.json 字段。关闭后提供推荐但不倒计时，继续独立工作；用户明确恢复后只对仍待决定的问题重新展示推荐并从发送时计时，不追溯原截止时间。用户暂停任务或停止队列优先。

- **每题推荐**：先通过[发问前检查](#发问前检查)，再发送具体推荐及适用的等待说明。尚未生成原型、测试失败或证据不足时，推荐补齐或修复，不能推荐虚构通过。
- **全流程适用**：Figma 原型已生成且 Agent 视觉检查通过、且没有必须取得明确回复的约束时，可推荐采用具体节点/版本进入开发，到期按默认策略采用。用户自测待反馈时按[测试责任](testing.md)推荐转由 Agent 完成真实验证；默认选择不把未执行测试变成通过。重要选型、修改端和范围问题同样提出有依据的推荐并计时。
- **事实与操作边界**：缺少账号、环境或业务数据时，推荐可执行的核实路径，到期执行核实或推进独立部分，不猜测值。发布、部署、权限或数据操作须满足已有具体授权和宿主限制；没有条件时推荐安全准备、预览或核实步骤。必需答复或批准仍保持待确认，依赖工作不因超时推进，不将沉默当作新增授权或绕过宿主强制审批、禁止事项。工单队列/持续监听的开启、停止后续接及版本升级仍遵循各自明确选择规则。
- **真实计时**：异步提问发送后记录每题发送时间、推荐内容与版本，截止为发送后 60 秒。使用可靠时间来源，不按工具调用次数、模型猜测或预选状态计时。等待时推进独立工作，单次等待工具不超过 60 秒，并处理新消息。
- **到期处理**：执行前检查策略是否仍启用、最新回复、暂停及方案变化；真实满 60 秒、无答复且前置条件满足时采用原推荐，简短告知用户并记录“按默认策略超时采用”，随后继续依赖流程。明确答复优先；含糊答复继续澄清，不视为未回复。多题分别处理，不把部分回答推定为全部同意。
- **变化与续接**：用户要求等待、否定推荐或新信息使推荐失效时停止旧计时；重提推荐后重新计时。旧题若曾注明“不适用超时”或没有展示推荐，先按新规则重发，不能追溯认定已到期。恢复会话先核对新消息和原时间记录；不能证明计时、持续执行或访问所需工具时如实标记限制，不伪称已后台执行。

统一提示示例：“推荐采用原型 v1 进入开发，依据是……。1 分钟内未回复将按默认策略采用此版本；你也可以提出修改或要求继续等待。” 推荐动作是否成功仍由实际执行证据决定。本策略不自动创建后台调度或跨会话唤醒。升级后新任务读取新规则，进行中的任务按[更新规则](updates.md)保留原版本；旧题未展示超时推荐时先重发，不能因为升级追溯采用。
