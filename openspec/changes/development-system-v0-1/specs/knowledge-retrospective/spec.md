## ADDED Requirements

### Requirement: 知识先在工程验证再提炼通用能力

体系 SHALL 将修复和需求实现中经过验证的经验记录为适用条件、问题原因、有效做法及证据。工程专属知识留在工程，跨工程方法使用合成案例验证后再提出个人仓库改进；规范性结论回写唯一规范入口，同类经验优先更新已有条目。

#### Scenario: 一次修复采用临时绕过方案
- **WHEN** 方案缺少验证或仅适用于一次性情况
- **THEN** 作为有局限的候选记录，不直接写成所有工程必须遵守的长期规则。

### Requirement: 复盘先手动验证再自动启用

体系 SHALL 在创建定时任务前手动运行一次完整复盘，由用户核对报告准确性与价值。第一版采用本机每天北京时间 23:00，仅处理已接入的 zkxw；后续工程显式接入后才纳入范围。成功创建调度与实际完成运行分别报告。

#### Scenario: 方案已确认但调度尚未创建
- **WHEN** 当前只交付复盘设计或 Skill 文件
- **THEN** 标记未启用自动执行，不宣称今晚会自动运行或已生成日报。

### Requirement: 本机执行如实报告运行条件

体系 SHALL 明确本地自动化依赖运行中的电脑、宿主应用和可访问的工程；读取远端还依赖网络与有效授权。自动化继承既有权限和服务限制，不自动启动、停止或重启工程服务。

#### Scenario: 夜间电脑或应用不可用
- **WHEN** 计划时刻无法执行
- **THEN** 不伪造该次成功报告；下次成功执行时根据持久进度处理遗漏内容，不依赖未经验证的调度自动重放。

### Requirement: 增量复盘可恢复且不遗漏失败来源

体系 SHALL 记录按来源区分的上次成功处理位置，以提交标识和适用的工单更新时间确定范围，失败来源不推进成功进度。检查关联提交、工单与已有验证证据；未提交修改仅提示存在，不直接提炼为通用规则。无证据的“测试通过”不得从提交文案推断。

#### Scenario: Git 可读但 Gitea 授权失效
- **WHEN** 只能完成部分来源分析
- **THEN** 报告部分完成、已覆盖范围与未覆盖来源，保留工单补齐位置；恢复后补齐并避免重复生成同一知识候选。

### Requirement: 次日可查看复盘报告

体系 SHALL 将有内容的复盘报告按工程时区日期保存至默认 `.local/agent/retros/YYYY-MM-DD.md`，维护同目录 `latest.md` 作为最近报告入口，并另存执行状态。报告属于忽略于 Git 的本地材料，通过聊天结果提供位置；同日重跑更新状态并保留已审阅信息，避免覆盖用户批注。

报告必须包含执行状态、实际范围、关联提交和工单、已完成变化、验证结果与缺口、候选知识、建议修改目标、用户待办和来源引用。区分“没有新增”“未执行”“部分完成”“失败”。

#### Scenario: 当天没有新增内容
- **WHEN** 全部所需来源检查成功且没有待总结变化
- **THEN** 仅更新无新增的执行状态，不创建重复空报告；最近报告保留原日期，不能冒充当天报告。

#### Scenario: 失败或候选知识需要关注
- **WHEN** 本次失败、部分完成或有待审阅事项
- **THEN** 提供清楚的结果入口与待办提示；状态不变且没有可操作事项时保持安静。通知偏好由宿主适配器按实际能力配置。

### Requirement: 复盘只形成草稿而不自动扩大变更

体系 SHALL 自动生成报告、知识候选及规则修改草稿，正式代码、规则、文件删除和公共能力发布按独立审查与授权处理。审核通过的工程经验进入知识或规范，通用能力通过个人仓库贡献与发布流程进入版本，再由其他工程主动升级。

#### Scenario: 复盘建议修改正式规则
- **WHEN** 报告提出改进 AGENTS、Skill、目录或测试约定
- **THEN** 写明理由、适用范围、依据和具体建议，由用户审阅后再实施；不能因为调度已获授权而自动提交、合并或发布该改动。
