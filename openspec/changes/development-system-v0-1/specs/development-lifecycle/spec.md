## ADDED Requirements

### Requirement: 关键疑问在依赖工作前确认

体系 SHALL 及早识别并澄清影响范围、业务、权限、数据、验收及重要选型的未知项，在答案明确前不定稿相关规格、不实施依赖该决定的业务代码。调查、候选材料与已授权独立工作遵循既有阶段门槛；具体步骤唯一维护于 [关键疑问先澄清](../../../../../skills/personal-dev/references/planning.md#关键疑问先澄清)。

#### Scenario: 用户催促但业务口径不明确
- **WHEN** 已有工单及修改端，但金额口径或权限范围尚未确认
- **THEN** 查阅已有依据后集中确认仍缺失的决定；可记录待确认项或候选方案，不将假设定稿或据此开发。

#### Scenario: 执行中新疑问与普通实现细节
- **WHEN** 开发中发现新的关键未知项，或仅需决定不改变外部行为的内部命名
- **THEN** 对前者暂停依赖部分并澄清，对后者按现有规范自主处理；沿用已有确认，不重新启动完整访谈。

### Requirement: 提问附推荐并按预授权处理三分钟未答复

体系 SHALL 每题提供推荐答案、理由及主要影响；需要事实的题提供核实路径。用户明确采用默认选择策略后，对已授权范围内有依据且可逆的普通选择，在发问时告知推荐及默认行为，真实等待 180 秒并检查最新回复后才可采用推荐。具体适用边界与计时唯一维护于 [提问推荐与三分钟默认选择](../../../../../skills/personal-dev/references/planning.md#提问推荐与三分钟默认选择)。不得将默认选择记为用户明确批准。

#### Scenario: 普通选择达到截止时间
- **WHEN** 用户已授权默认策略，题目已展示推荐和超时行为，真实经过 180 秒且仍无答复或暂停
- **THEN** 记录按预授权采用原推荐并告知用户，再继续依赖工作；未满 180 秒不提前采用。

#### Scenario: 必答事项或未核实事实
- **WHEN** 问题涉及必须明确的验收、另需授权的操作或缺少真实信息
- **THEN** 给出建议并保留待确认或待核实状态，不能超时批准、扩权或推定测试通过。

#### Scenario: 部分回答或修改推荐
- **WHEN** 多题仅部分回答，用户要求等待，或新信息导致推荐变化
- **THEN** 分题处理，尊重答复和暂停；变更推荐重新展示计时，无法核对时间或持续执行时报告限制，不伪称已自动继续。

### Requirement: 工程选型覆盖完整生命周期

体系 SHALL 在新工程开发前根据整体需求确认技术栈、范围、架构、目录职责、验收条件及环境和发布方式。已有工程以当前稳定技术栈为基线；需求演变导致技术调整时记录原因、影响、迁移和验证方案，由用户确认重要选型决策。

#### Scenario: 新工程不继承试点的技术栈
- **WHEN** 接入一个空白工程
- **THEN** 依据该工程大需求确认选型和应用范围，不默认生成 zkxw 的四应用结构或复制其历史依赖版本。

#### Scenario: 已有工程发生技术演进
- **WHEN** 新需求无法由现有架构合理满足
- **THEN** 先评估技术变更及迁移影响，确认后实施，并同步工程决策入口；不把偶然安装的新依赖视为已批准选型。

### Requirement: 正式开发以可追溯工单为入口

体系 SHALL 将正式功能和 Bug 关联至 Gitea 工单，至少包含诉求、影响范围和可检查的验收条件；聊天可用于澄清。新能力、业务规则变化、跨模块或接口变更使用完整 OpenSpec；局部行为恢复使用复现、方案和回归证据，发现规范错误或缺失时补充对应规范。

#### Scenario: 用户未提供工单编号
- **WHEN** 用户提出正式需求或 Bug，未给工单编号且当前任务没有明确关联工单
- **THEN** 在工程已有授权内由 AI 先创建 Gitea 工单，取得编号后实施；不要求用户代建。连接或权限不可用时说明阻碍，只继续独立的只读定位，不虚构工单已创建。

#### Scenario: 用户提供编号或继续已关联任务
- **WHEN** 用户提供 Gitea 编号/链接，或继续当前已明确关联工单的任务
- **THEN** 读取该工单描述、评论与验收条件后处理；复用该工单而非重复创建。

#### Scenario: 局部 Bug 与规格变更区分处理
- **WHEN** 工单要求恢复已约定的行为，且不改变业务规则或接口
- **THEN** 记录复现与回归验证即可，不重复生成完整规格；若调查发现需求语义发生变化，升级为规格变更流程。

#### Scenario: 轻量任务不生成重复材料
- **WHEN** 任务是纯咨询、一次性连接验证或无行为变化的小文字修正
- **THEN** 允许简化工单和流程，保留适用的任务依据与检查结果；不能借此绕过实际业务变更的验收。

### Requirement: 修改端不明确时先确认范围

体系 SHALL 在实施前读取当前任务对话及工单的已确认应用范围。范围不明确时，询问用户修改哪些端或所有相关端，按工程实际应用提供选项；截图和当前目录只作为定位线索。待确认期间可以只读定位、创建或更新工单并标记范围待确认，SHALL 在确认后修改业务代码并回写具体应用和验收范围。

#### Scenario: 未说明端且截图看起来属于 Web
- **WHEN** 用户提出问题但未明确修改端，已有任务记录也未确认范围
- **THEN** 先询问修改哪些端或所有相关端，不凭截图推定 Web，不默认跨端同步修改；未得到答复前不修改业务代码。

#### Scenario: 既有范围明确或用户选择所有端
- **WHEN** 当前任务或工单已有明确范围，或用户答复所有相关端
- **THEN** 沿用已有结论，不重复询问；将所有相关端落实为工程中的具体应用清单，写入工单和验收范围。

#### Scenario: 共享后端影响已确认范围之外的端
- **WHEN** 拟议的共享后端或 API 变更会影响其他端
- **THEN** 先说明连带影响并确认范围扩展，再实施，不从共享实现推断跨端修改授权。

### Requirement: 新界面与弹窗先经 Figma 原型确认

体系 SHALL 对新页面、新弹窗及用户要求的视觉改版，先制作可编辑 Figma 原型并关联具体文件或节点，用户明确确认后继续业务界面实现；简单程度和已有组件不免除该步骤。只有用户明确本任务不用生成 Figma 原型时才豁免，并记录范围，仍保留视觉规范和最终验证。具体执行见 [界面原型与确认](../../../../../skills/personal-dev/references/ui-design.md)。

#### Scenario: 单字段弹窗且有现成组件
- **WHEN** 新弹窗只有单个输入框且已有匹配组件
- **THEN** 在 Figma 中复用相应设计并取得用户确认后实现，不直接跳过原型。

#### Scenario: 原型尚未确认
- **WHEN** 原型完成但用户尚未明确确认
- **THEN** 将状态标为待原型确认，不能以工具生成成功代替用户同意继续实现。

#### Scenario: 用户仅要求代码完成后再看
- **WHEN** 用户催促实现或要求完成代码后再看，但未明确不用 Figma 原型
- **THEN** 提供具体原型并确认，不把延期验收视为原型豁免或批准。

#### Scenario: 用户明确不生成原型
- **WHEN** 用户明确本任务不用 Figma 原型
- **THEN** 记录本任务的豁免范围后继续，不重复请求相同豁免，不推广到后续任务。

### Requirement: 界面实现以可追溯参考和实际视觉证据验收

体系 SHALL 在界面实现及布局样式修改时，记录同端同类参考、组件复用和规范依据，处理历史实现冲突，并按测试责任验证实际效果。原型豁免不免除一致性要求。执行与沉淀步骤统一见 [界面一致性、原型与验收](../../../../../skills/personal-dev/references/ui-design.md)。

#### Scenario: 确认提示样式用于编辑表单
- **WHEN** 可用组件的交互类型与任务不同
- **THEN** 检查适用性及能力缺口，选择符合规范的复用或扩展方案，不能只拼接 CSS 作为复用完成证据。

#### Scenario: 功能测试通过但尚未查看实际渲染
- **WHEN** Agent 模式的界面功能测试和编译通过，但缺少必要的视觉检查
- **THEN** 保持待视觉验证，取得实际版本与主要状态的对照证据后交付；用户模式仍由用户验收，不擅自替代测试。

### Requirement: 分支与 worktree 共同隔离正式实现

体系 SHALL 为正式功能或 Bug 创建独立任务分支和对应 worktree，从最新且已核实的工程集成分支开始；已有任务复用其隔离工作区。优先宿主原生 worktree，不可用于目标仓库时采用工程约定的 Git worktree。测试数据库、端口和凭据单独隔离，worktree 不代表测试环境已隔离。

#### Scenario: 任务工作区已存在
- **WHEN** 继续同一工单且已有对应分支与 worktree
- **THEN** 核对未提交内容和任务归属后复用，不创建第二份相互竞争的工作区；保留主目录及其他任务改动。

### Requirement: 测试责任分为 Agent 与用户两种模式

体系 SHALL 默认由 Agent 在任务分支或 worktree 完成测试，核对实际运行代码与待验收提交。用户明确自己测试时，该任务 SHALL 改用用户测试模式：Agent 完成代码和审查，不运行自动测试、构建或替代性业务验收，仍核对 Git 状态、源码和提交。模式和验收提交记录在工单中。

#### Scenario: 默认 Agent 测试
- **WHEN** 用户未指定自己测试
- **THEN** Agent 保留本地改动，自动进入对应分支/worktree，核对运行目录、端口和代码，执行与影响相符的测试；通过且审查无阻塞后继续自动收尾。工程的服务启停限制不因测试模式改变。

#### Scenario: 用户明确自己测试
- **WHEN** 用户表示“我来测试”或同等意思
- **THEN** Agent 不执行测试和构建，完成实现与审查后标注待用户测试，提醒用户切换到具体分支，提供 worktree 路径、提交、入口、覆盖点与预期结果；指出配套前后端版本，等待用户确认通过，不提前合并或关单。

#### Scenario: 用户测试失败后继续修复
- **WHEN** 用户测试模式下继续反馈问题
- **THEN** 修复后再次交付用户测试，不擅自切回 Agent 模式；用户确认通过后直接合并、推送并关闭工单，不重复请求合并授权。

### Requirement: 验证状态以实际证据为准

体系 SHALL 按测试责任记录实际命令结果或用户验收确认，区分基线失败、新增失败和未执行项。重要业务变更经独立审查。Agent 模式缺少必要测试环境或平台时保持待验证；用户模式不将静态审查冒充用户已通过。

#### Scenario: 必要测试无法完成
- **WHEN** Agent 测试所需环境或平台不可用，或用户测试模式尚未收到通过确认
- **THEN** 说明阻碍和剩余责任，保留工单开放，不自行将结果标为通过或切换测试责任。

### Requirement: 已采用自动收尾流程的工程不重复请求授权

体系 SHALL 将用户明确采用自动收尾流程视为工程常规任务的持续授权，覆盖任务分支推送、PR、工单回写及已指定集成分支合并。按测试责任取得通过证据后直接执行。仅安装 Skill 不构成外部授权，Tag、部署和服务启停仍分别遵守工程授权。

#### Scenario: 已有持续授权且 Agent 测试通过
- **WHEN** 用户已采用自动收尾流程，Agent 完成必要测试和审查
- **THEN** 自动合入指定集成分支并提交推送，核对远端后关闭工单，不停在 PR 或重复询问是否合并。

#### Scenario: 用户确认指定提交测试通过
- **WHEN** 用户测试模式下用户确认待验收提交通过
- **THEN** 自动完成本任务合并、提交推送及关单，不要求用户再次发出合并指令。

#### Scenario: 未采用流程的工程没有远端授权
- **WHEN** 仅安装技能且没有工程或当前任务的相关授权
- **THEN** 不从技能存在推断外部写权限；核对授权缺口后处理。

### Requirement: 合并结果与验收版本一致后关闭工单

体系 SHALL 核对最新目标分支、被测试提交及合并代码，使用 Git 合并而非复制目录。代码树与验收版本一致时保留原测试证据，不重复测试；目标更新或冲突处理改变代码时，按同一测试模式补验，通过前不推送集成结果或关闭工单。合并推送成功后同步当前工程到集成分支，在工单记录测试责任、验收、合并提交与 PR，再关闭工单并按工程策略清理。

#### Scenario: 用户测试后目标分支变化
- **WHEN** 用户已通过但新目标或冲突处理改变了合并代码
- **THEN** 在隔离集成分支准备结果并再次交由用户验证，Agent 不代跑测试；通过前不推送主版本或关闭工单。

#### Scenario: 合并已完成但远端推送失败
- **WHEN** 本地合并成功但远端同步未成功
- **THEN** 报告并处理失败，保持工单开放，不把本地提交当作完成远端交付。

### Requirement: 推送 Tag 触发 Drone 打包

体系 SHALL 将打包作为合并后的独立动作：在确认且验证通过的提交上按工程版本约定创建 Tag，并在用户指令或预先授权下推送至 Gitea。一次打包可包含多个已合并工单。记录 Tag、提交、构建结果及产物位置；已发布 Tag 不随意移动或覆盖。打包与生产部署分别定义和授权。

#### Scenario: 本地 Tag 尚未推送
- **WHEN** 仅完成本地 Tag 创建
- **THEN** 不宣称 Drone 已收到触发或构建成功；推送后检查流水线及产物结果。

#### Scenario: 新工程完成构建接入
- **WHEN** 初始化新工程的 Gitea 与 Drone
- **THEN** 按确认的技术栈配置构建、产物和 Tag 触发规则，并通过已授权的测试 Tag 实际验证产物可获取，才标记打包链路完成。

#### Scenario: 已由用户确认完成的试点流水线
- **WHEN** 接入 zkxw 的既有 Drone Tag 打包流程
- **THEN** 沿用用户确认的配置，不安排重新核对或修改该流水线；后续实际打包仍核对目标提交、授权与本次构建结果。
