## ADDED Requirements

### Requirement: 工程选型覆盖完整生命周期

体系 SHALL 在新工程开发前根据整体需求确认技术栈、范围、架构、目录职责、验收条件及环境和发布方式。已有工程以当前稳定技术栈为基线；需求演变导致技术调整时记录原因、影响、迁移和验证方案，由用户确认重要选型决策。

#### Scenario: 新工程不继承试点的技术栈
- **WHEN** 接入一个空白工程
- **THEN** 依据该工程大需求确认选型和应用范围，不默认生成 zkxw 的四应用结构或复制其历史依赖版本。

#### Scenario: 已有工程发生技术演进
- **WHEN** 新需求无法由现有架构合理满足
- **THEN** 先评估技术变更及迁移影响，确认后实施，并同步工程决策入口；不把偶然安装的新依赖视为已批准选型。

### Requirement: 正式开发以可追溯工单为入口

体系 SHALL 将正式功能和 Bug 关联至 Gitea 工单，至少包含诉求、影响范围和可检查的验收条件；聊天可用于澄清。新能力、业务规则变化、跨模块或接口变更使用完整 OpenSpec；局部行为恢复使用复现、方案和回归证据，发现规范错误或缺失时补充对应规范。

#### Scenario: 用户未提供工单编号
- **WHEN** 用户提出正式需求或 Bug，未给工单编号且当前任务没有明确关联工单
- **THEN** 在工程已有授权内由 AI 先创建 Gitea 工单，取得编号后实施；不要求用户代建。连接或权限不可用时说明阻碍，只继续独立的只读定位，不虚构工单已创建。

#### Scenario: 用户提供编号或继续已关联任务
- **WHEN** 用户提供 Gitea 编号/链接，或继续当前已明确关联工单的任务
- **THEN** 读取该工单描述、评论与验收条件后处理；复用该工单而非重复创建。

#### Scenario: 局部 Bug 与规格变更区分处理
- **WHEN** 工单要求恢复已约定的行为，且不改变业务规则或接口
- **THEN** 记录复现与回归验证即可，不重复生成完整规格；若调查发现需求语义发生变化，升级为规格变更流程。

#### Scenario: 轻量任务不生成重复材料
- **WHEN** 任务是纯咨询、一次性连接验证或无行为变化的小文字修正
- **THEN** 允许简化工单和流程，保留适用的任务依据与检查结果；不能借此绕过实际业务变更的验收。

### Requirement: 复杂且无参考的界面先做 Figma

体系 SHALL 在复杂界面且工程内缺少可参考实现时，先制作 Figma 原型并关联具体文件或节点，用户验收通过后继续实现。用户明确要求直到代码完成才验收时，仅跳过该任务的中途人工验收，仍保留必要原型、自检和最终验收。业务与权限要求由规格表达。

#### Scenario: 缺少参考且没有延期验收指令
- **WHEN** 复杂界面原型完成但用户尚未验收
- **THEN** 将状态标为待界面验收，不能以工具生成成功代替用户同意继续实现。

#### Scenario: 用户要求代码完成后再验收
- **WHEN** 用户对指定任务明确延期人工验收
- **THEN** 完成原型与自检后继续实现，并保留最终验收；不能把此例外推广至其他任务。

### Requirement: 分支与 worktree 共同隔离正式实现

体系 SHALL 为正式功能或 Bug 创建独立任务分支和对应 worktree，从最新且已核实的工程集成分支开始；已有任务复用其隔离工作区。优先宿主原生 worktree，不可用于目标仓库时采用工程约定的 Git worktree。测试数据库、端口和凭据单独隔离，worktree 不代表测试环境已隔离。

#### Scenario: 任务工作区已存在
- **WHEN** 继续同一工单且已有对应分支与 worktree
- **THEN** 核对未提交内容和任务归属后复用，不创建第二份相互竞争的工作区；保留主目录及其他任务改动。

### Requirement: 验证状态以实际证据为准

体系 SHALL 按应用与改动范围选择验证，报告实际执行的命令、环境、提交、结果和未执行项；区分既有失败与新增失败。重要业务变更经独立审查。缺少数据库、目标平台、人工验收或其他必要条件时保持待验证，不能以自查代替缺失证据，不能默认连接真实业务数据库。

#### Scenario: 小程序尚无目标平台验证
- **WHEN** 静态检查通过，但任务要求的平台编译或真机验证未执行
- **THEN** 明确列出剩余验证及负责方，不宣称任务已全部验证或满足合并条件。

### Requirement: 推送任务分支与合并集成分支分别授权

体系 SHALL 根据工程授权推送任务分支、创建 PR 并回写当前任务的工单或 PR。合并集成分支需要明确指令或该任务已有的合并授权；已授权步骤不重复询问。未通过验证的草稿 PR 必须明确标记缺口，不呈现为可合并。

#### Scenario: 工程允许推送但未授权合并
- **WHEN** 任务验证与审查通过
- **THEN** 推送任务分支并创建目标为工程集成分支的 PR，保留待合并状态；不直接推送或合入集成分支。

#### Scenario: 目标分支在开发期间已更新
- **WHEN** 准备执行已授权的合并
- **THEN** 核对当前目标分支及审查过的提交；同步其他更新、处理冲突并重新验证受影响范围，满足条件后合并提交，而不是复制 worktree 文件。

#### Scenario: 修复已提交但尚未完成集成验收
- **WHEN** 修复代码及验证证据已提交，尚有用户验收、合并或发布事项
- **THEN** 工单标注“已修复”，附提交、PR、验证结果及剩余事项；分别注明验收、合并和发布状态，不提前关闭工单。

### Requirement: 合并后仍有集成验收与清理阶段

体系 SHALL 在合并后的集成分支上执行相关回归；满足工单验收条件后才关闭工单。回归失败时保持任务未完成，处理修复或按授权回退。验证、合并和交付记录已保留后，按工程策略归档或清理 worktree，核查未提交及未推送内容后处理任务分支。

#### Scenario: 合并成功但集成回归失败
- **WHEN** PR 已合并但相关集成测试失败
- **THEN** 报告失败和影响，工单不标记完成，不进入发布就绪状态。

### Requirement: 推送 Tag 触发 Drone 打包

体系 SHALL 将打包作为合并后的独立动作：在确认且验证通过的提交上按工程版本约定创建 Tag，并在用户指令或预先授权下推送至 Gitea。一次打包可包含多个已合并工单。记录 Tag、提交、构建结果及产物位置；已发布 Tag 不随意移动或覆盖。打包与生产部署分别定义和授权。

#### Scenario: 本地 Tag 尚未推送
- **WHEN** 仅完成本地 Tag 创建
- **THEN** 不宣称 Drone 已收到触发或构建成功；推送后检查流水线及产物结果。

#### Scenario: 新工程完成构建接入
- **WHEN** 初始化新工程的 Gitea 与 Drone
- **THEN** 按确认的技术栈配置构建、产物和 Tag 触发规则，并通过已授权的测试 Tag 实际验证产物可获取，才标记打包链路完成。

#### Scenario: 已由用户确认完成的试点流水线
- **WHEN** 接入 zkxw 的既有 Drone Tag 打包流程
- **THEN** 沿用用户确认的配置，不安排重新核对或修改该流水线；后续实际打包仍核对目标提交、授权与本次构建结果。
